This skill defines the architectural requirements and standards for testing all API implementations.

## Core Principles: The Testing Pyramid
1. **Unit Tests**: Fast, isolated (mocked), covering domain logic. No database, no broker, no HTTP server.
2. **Integration Tests**: Infrastructure-focused (DB, Broker, Cache), requires Docker. Validates repository implementations, event serialization, and outbox polling.
3. **Application Tests**: End-to-end HTTP flows against the projected API. Spins up the full application context (or a test server) and exercises REST endpoints.

## Testing Event-Driven Architectures (CQRS)
To prevent non-deterministic failures in test suites, the Builder MUST adhere to:

### 1. Asynchronous Assertion Strategy
Application tests that trigger cross-module workflows MUST NOT use synchronous assertions.
- **Polling**: Use an asynchronous polling mechanism native to the language.
- **Timeout Law**:
    - **Default Timeout**: 5 seconds.
    - **Poll Interval**: 100 milliseconds.
- **Fail Fast**: If the condition is not met within the timeout, the test MUST fail with a clear "Eventual Consistency Failure" message.

#### Per-Language Polling Libraries
| Stack | Polling Mechanism | Example |
|---|---|---|
| Java / Spring | Awaitility (`org.awaitility`) | `await().atMost(5, SECONDS).until(() -> repo.exists(id))` |
| Kotlin / Ktor | `kotlinx.coroutines` + `withTimeoutOrNull` | Custom polling loop with delay |
| Go / Gin | Custom retry loop or `testify/assert` + `time.Sleep` | `assert.Eventually(t, fn, 5s, 100ms)` |
| Rust / Axum | `tokio::time::timeout` + `tokio::time::sleep` | Retry loop with `tokio::time::sleep(Duration::from_millis(100))` |

### 2. Idempotency Verification
Every integration test for an Event Subscriber MUST execute the same event TWICE to verify that the **Inbox Pattern** (Idempotency) is correctly implemented and doesn't create duplicate side effects.

### 3. Testcontainers Integration
Integration and Application tests MUST use ephemeral infrastructure. The preferred approach is Testcontainers or language-equivalent Docker orchestration:
- **Java / Kotlin**: Testcontainers (`PostgreSQLContainer`, `RabbitMQContainer`, `GenericContainer` for Redis).
- **Go**: `testcontainers-go`.
- **Rust**: `testcontainers-rs`.

If Testcontainers is unavailable for the target stack, the test harness MUST spin up Docker Compose services before the test suite and tear them down after.

## Per-Stack Test Runner Configuration

| Concern | Java / Spring | Kotlin / Ktor | Go / Gin | Rust / Axum |
|---|---|---|---|---|
| **Unit Test Runner** | JUnit 5 + AssertJ | JUnit 5 + AssertJ / Strikt | `testing` (stdlib) + `testify` | `cargo test` + `tokio-test` |
| **Mocking** | Mockito | MockK | `mockery` / `gomock` / manual interfaces | Manual trait mocks / `mockall` |
| **HTTP Test Client** | `MockMvc` / `TestRestTemplate` | Ktor `TestApplicationEngine` | `httptest` + `gin.CreateTestContext` | `axum::Server` + `reqwest` |
| **DB Test Fixture** | `@DataJpaTest` / `@SpringBootTest` | Manual setup with Testcontainers | `pgxpool` against Testcontainer Postgres | `sqlx::Pool` against Testcontainer Postgres |
| **Async Test** | `@Async` / `CompletableFuture` | `runBlockingTest` | Goroutines | `#[tokio::test]` |

## Benchmarking
In addition to functional tests, every implementation MUST provide a benchmark harness conforming to `@shared/skills/testing/benchmarking`. The benchmark is not a correctness test; it is a performance characterization tool that enables cross-implementation comparison.

- The benchmark harness is generated by the Builder as part of the standard projection.
- It runs via `make benchmark` and emits `benchmark-report.json`.
- Benchmark reports from different targets can be compared using `make benchmark-compare`.

## Coverage Gate
- **Minimum Line Coverage**: 70% for Unit + Integration combined.
- **Mandatory Coverage Areas**:
    - All Command Handlers (happy path + all domain error branches).
    - All Query Handlers (filtering, pagination, sorting).
    - All Event Subscribers (inbox deduplication, projection updates).
    - All REST endpoints (auth failure, validation failure, success).
