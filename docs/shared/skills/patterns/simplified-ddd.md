# Skill: Simplified DDD Approach

This skill defines the architectural patterns for a "Simplified Domain Driven Design" (DDD) to be applied across all implementations.

## Core Principles

1.  **Ubiquitous Language**: All technical identifiers (classes, variables, tables) must match the terms defined in `docs/specs/[module]/definitions`.
2.  **Layers & Internal Package Structure**: Each module must be projected into a **Hexagonal (Ports & Adapters)** directory structure:
    *   **Domain Layer** (`domain/`): Pure business logic.
        *   `models/`: Domain Aggregates (Write Model).
        *   `projections/`: Read Models (UI Model).
        *   `values/`: Value Objects.
        *   `errors/`: Domain Errors.
        *   `events/`: Definitions of Domain Events emitted by this module.
        *   `ports/`: All **Required Interfaces** (Outbound Ports) needed by the domain (e.g., `PersonRepository`, `NotificationPort`).
    *   **Application Layer** (`application/`):
        *   `commands/`: State-changing logic components.
        *   `queries/`: Side-effect-free data retrieval components.
    *   **Presentation Layer** (`presentation/`): **Driving Adapters** (Inbound).
        *   `rest/`: Adapts HTTP requests (derived from `specs/[module]/presentation/rest/`).
        *   `subscribers/`: Adapts incoming Events (derived from `specs/[module]/presentation/subscribers/`).
    *   **Infrastructure Layer** (`infrastructure/`): **Driven Adapters** (Outbound).
        *   `persistence/[provider]/`: Implementation of Repository Ports.
        *   `messaging/[provider]/`: Implementation of Event Publisher/Subscriber Ports.
        *   `mappers/`: Data mappers between layers.
3.  **Encapsulation & Value Objects**:
    *   Entities must maintain their own consistency.
    *   Value Objects are mandatory for attributes with complex validation logic or constrained types (e.g., `Email`, `Currency`, `PersonId`). They must be immutable and self-validating.
4.  **Ports & Adapters (Decoupling Law)**:
    *   The Domain and Application layers MUST NOT depend on the Infrastructure or Presentation layers.
    *   All communication with external systems (DB, Broker, APIs) MUST happen through an interface defined in `domain/ports/`.

5.  **Data Mapping**:
    *   Mappers are mandatory. The Builder must synthesize mappers to convert between Infrastructure Entities and Domain Models, and between Domain Models and Presentation DTOs.
6.  **Persistence Tuning Law**:
    *   Any field used in a Domain Repository lookup method (e.g., `findByEmail`, `existsByPersonId`) MUST be explicitly supported by a dedicated index in the database schema.
    *   This index must be defined via explicit Migration scripts, never relying on ORM auto-generation or annotations.
7.  **Explicit Domain Errors**:
    *   Generic domain errors are forbidden. The Builder MUST synthesize specific Domain Errors for every error defined in the specs (e.g., `PersonNotFound`, `InvalidEmail`). 
    *   These errors must be implemented idiomatically according to the target language (e.g., Custom Exception classes in Java/Kotlin inheriting from a base `DomainException`, or custom `error` types in Go/Rust) and must reside in the `domain/errors/` package.
    *   The Presentation layer must map these specific errors to appropriate HTTP statuses.
    *   **Error Handling Law**: The Application Layer is **strictly forbidden** from leaking infrastructure or framework exceptions/errors to the Presentation Layer. Every technical failure must be captured and translated into an explicit Domain Error defined in the specs, ensuring the response is always domain-rich regardless of the language's error handling style (Exceptions vs. Results).
8.  **Law of Identity (Application-Side Generation)**:
    *   To support idempotency and reliable event tracing, unique identifiers (`id`) MUST be generated by the **Application Layer** (Use Case) before persistence. 
    - Relying on database-side auto-increment or `DEFAULT gen_random_uuid()` is forbidden for primary keys.
    - The implementation MUST use a standard logging abstraction (e.g., SLF4J for JVM, `log` for Go) and adhere to the following levels: `INFO` for business flows, `WARN` for recovered failures, and `ERROR` for unhandled exceptions.
10. **Binary Independence Law (Two-Runtime Deployment)**:
    - Each module MUST be architected to support multiple runtime "Target Binaries" from the same codebase.
    - A developer/agent must be able to compile a **Rest-API Binary** (initializing only `presentation/rest/` adapters) and an **Event-Processor Binary** (initializing only `presentation/subscribers/` adapters) by simply toggling adapter registration.
    - Domain and Application logic MUST remain perfectly identical across all binaries.

11. **Projection Purity Law**:
    - Read Models and Projections MUST be strictly read-only.
    - Projections MUST NOT be used to enforce domain invariants or business rules within a Command.
    - Commands MUST ONLY rely on the Source of Truth (Aggregates) or specific Outbound Ports.

12. **Multi-Tenancy Isolation Law (Logical Ownership)**:
    - Every Domain Aggregate and Projection (outside the `Identity` global scope) MUST include a `tenantId`.
    - Every Command and Query MUST accept a `tenantId` as a mandatory input parameter.
    - All persistence operations MUST strictly filter by this `tenantId`.
    - In this Personal Ledger ecosystem, the `tenantId` is functionally equivalent to the `userId`.
    - All queries and commands MUST strictly filter by the `tenantId` (The Owner) provided by the `sub` claim in the authenticated context.
    - Data leaking between users is a critical architectural failure.

13. **Sharding Law (Physical Partitioning)**:
    - To support millions of users, the system uses **Shard-Based Routing**.
    - The `sid` claim in the JWT identifies which physical shard/database contains the user's data.
    - Cross-shard transactions are forbidden. A single user's data MUST reside on a single shard.

14. **Observability Law (Total Traceability)**:
    - Every Command, Query, and Subscriber MUST be instrumented with an OpenTelemetry Span.
    - Spans MUST include the `tenantId` and `shardId` as attributes for high-resolution debugging.
    - Distributed Tracing MUST be maintained across messaging boundaries (Outbox $\rightarrow$ Broker $\rightarrow$ Subscriber).

15. **Persistence Segregation Law (Physical CQRS)**:
    - **WRITE_DB**: Contains ONLY Domain Aggregates (Source of Truth).
    - **READ_DB**: Contains ALL Projections and Read Models (Display and Validation data).
    - **Zero Physical Coupling**: No Foreign Keys or JOINs are allowed between the `WRITE_DB` and `READ_DB`.
    - **Asynchronous Integrity**: The Command Layer (Write) may query the `READ_DB` for non-critical validation, accepting that the Read Side is eventually consistent.

## Implementation Rules

*   **Strict CQRS Enforcement**: The system strictly adheres to the rules defined in `@shared/skills/patterns/cqrs-and-events`.
*   Each `specs/[module]/commands` behavior corresponds to exactly one **Command Handler** in the `application/commands/` layer.
*   Each `specs/[module]/queries` behavior corresponds to exactly one **Query Handler** in the `application/queries/` layer.
*   Each `specs/[module]/presentation/subscribers/` behavior MUST be projected into a **Driving Adapter** in `presentation/subscribers/` that delegates to an Application Command.
*   Each `specs/[module]/presentation/rest/` behavior corresponds to a **Driving Adapter** in `presentation/rest/`.
*   Each `specs/[module]/models` file corresponds to a pure entity/aggregate in the Domain Layer (Write Model).
*   Each `specs/[module]/projections` file corresponds to a Read Model in the Domain Layer (UI Model).
